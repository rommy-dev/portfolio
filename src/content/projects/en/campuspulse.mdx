## Problem

ESPA Vontovorona has no figures on how its students get around, use water and energy, eat or sort their waste. Without that data, student requests and campus planning choices rest on impressions.

## My contribution

Academic project built solo for a course, in August and September 2026: survey, database schema, access policies, interface, dashboard and Excel export.

## Solution

**For students**

- A 9-step survey (transport, budget and water, food, digital, clothing, hygiene, waste, perception of the campus, general information).
- One submission per account, enforced by the database.
- Access to the survey's aggregated statistics.

**For the administration**

- Dashboard: registered users, complete responses, people to follow up with, response rate.
- Detailed statistics by topic, with charts.
- Multi-sheet Excel export (wide view and detailed view) and user account management.

## Results

<Metrics />

The survey was shared with a small group of students to test it: 30 signed up and 22 filled in the whole survey. The ESPA administration did not adopt the tool. The figure of 22 dates from September 2026 and is no longer updated.

## Try it

<TryIt />

You can try the demo with the student role: create an account in the application, then fill in the survey and browse the statistics.

There is no demo admin account, for privacy reasons: that role gives access to the accounts of the students who took part in the test. The admin dashboard is shown in the screenshots in the overview (September 2026).

### Architecture

<Diagram />

Supabase provides authentication, the PostgreSQL database and avatar storage. The React application reads from and writes to Supabase directly; access is filtered by Row Level Security policies. Statistics are computed in the database by two SQL functions that only return counts: `get_public_landing_kpis()` for the home page, `get_survey_stats()` for the Statistics page. An in-memory cache and `localStorage` avoid reloading the home page indicators on every visit.

### Security

Row Level Security is enabled on the `profiles` and `responses` tables. Who can read what, according to the policies in place:

| Role | Responses (`responses`) | Profiles (`profiles`) |
| --- | --- | --- |
| Signed-out visitor | No rows. Only 4 aggregated indicators via `get_public_landing_kpis()` | None |
| Signed-in student | Create and read their own response. Per-question counts via `get_survey_stats()` | Read and edit their own profile |
| Admin | Read all responses | Read, edit and delete all profiles |

No policy allows a response to be edited or deleted. Example of an actual policy (initial migration; the policy name is in French in the code):

```sql
create policy "Un utilisateur cree sa propre reponse"
  on public.responses for insert
  with check (auth.uid() = user_id);
```

Admin status is checked by an `is_admin()` function declared `security definer`, which avoids infinite recursion between the `profiles` policies.

November 2026 fix: previously, any signed-in account could read the raw responses, because the Statistics page computed the charts in the browser. Now `get_survey_stats()` only returns counts, limited to the questions shown on screen: never the date of birth, exact age, field of study, year of study or free-text answers.

### Testing and quality

The repository has no automated tests. Checks were done by hand.
